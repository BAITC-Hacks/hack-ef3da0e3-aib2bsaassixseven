# Meeting Intelligence MVP — актуальный дизайн системы

Статус: документация на проверке, реализация встреч ещё не начата.
Ветка: `yernur-backend`. Исходная спецификация от 2026-09-23 уточнена по новому решению команды о NVIDIA-сервере.

## Решение

Пользователь загружает аудиофайл на сайте. FastAPI приложения передаёт его на выделенный NVIDIA-сервер команды с собственной запущенной моделью. Сервер распознаёт речь, разделяет спикеров, формирует саммари и поручения. Backend сохраняет результаты в локальную папку `data/`, frontend показывает удобный дашборд. После подтверждения сохранения временная запись GPU-сервера и upload-копия приложения удаляются.

Эта схема заменяет прежний дизайн «ML worker и все данные на одной машине приложения». Под локальным сохранением пока понимается диск backend приложения. Общий диск с NVIDIA-сервером не требуется.

## Пользовательский результат

Загрузка → обработка на NVIDIA → транскрипт/спикеры/саммари/поручения → дашборд → проверка и исправления → утверждение → PDF.

P0 сохраняет русский, казахский и смешанную речь, evidence-цитаты и таймкоды, nullable ответственного/срок, ручное сопоставление спикеров и обязательную проверку человеком. Ответственный может не говорить на встрече или быть подразделением; отсутствующий срок не выдумывается, исходная формулировка сохраняется. Каждый голос должен быть проверен: пользователь указывает имя/метку или явно подтверждает «Неизвестный спикер»; подтверждённая неизвестность разрешает approval. Точность и скорость выбранных моделей предстоит измерить на контрольных записях.

После удаления аудио evidence продолжает работать по сохранённому транскрипту. Серверное воспроизведение удалённой записи не обещается. Результаты можно открыть при недоступном NVIDIA-сервере.

## Runtime и данные

- Next.js — интерфейс загрузки, дашборд, проверка и экспорт.
- FastAPI приложения — доступ/ownership, временный upload, возобновляемая передача на GPU, сохранение результата, review и PDF.
- NVIDIA inference API и один Python-worker — локальные модели Erasyl, временные задания и очистка.
- Постоянное `data/users/<owner>/meetings/<id>/` приложения содержит `meeting.json`, `transcript.json`, `transcript.txt`, `insights.json`, `review.json`, `exports/protocol.pdf`.
- Временные `tmp/upload.*` приложения и `GPU_TEMP_ROOT/<job_id>/` не являются архивом аудио; исключены из Git.
- Docker, Redis и продуктовая БД не требуются. Supabase пока используется только существующим Auth/profile.

## Надёжность передачи и удаления

1. Upload сохраняется временно вместе с manifest, API отвечает `202 queued`.
2. Coordinator API передаёт задачу с idempotency key и сохраняет GPU job ID.
3. Worker GPU выдаёт `TranscriptV1` и `InsightsV1` (`schema_version: 1`) в `ResultBundleV1` с версиями моделей и SHA-256 `result_hash` по [API Contract](../../technical/API_CONTRACT.md).
4. Backend валидирует и атомарно публикует результат, затем подтверждает его сохранение GPU-серверу.
5. GPU удаляет аудио, производные медиа и временный результат; backend удаляет свой upload. Сбой очистки отображается как pending и повторяется.
6. Начальный TTL временных данных — 24 часа от приёма на каждой машине, без продления повторами; он действует также для неудачных или брошенных задач. После TTL для нового inference может потребоваться повторная загрузка.
7. Сбой сохранения на стороне приложения не разрешает досрочное удаление по ACK. Истечение TTL остаётся независимым пределом хранения.

Интерфейс использует состояния queued, processing, review_required, approved, failed. Стадии передачи на GPU и сохранения результата отделены от стадий ML. Повтор ACK/получения результата не запускает модель заново. Квитанция GPU хранится 7 суток после подтверждённой очистки; её отсутствие не считается успехом удаления. PDF формируется локально после человеческого утверждения; правки требуют нового approval.

## Схемы и проверка

Единый источник полей и JSON-примеров — [API Contract](../../technical/API_CONTRACT.md). Метки голосов остаются стабильными строками `speaker_N`; сегменты и пункты имеют UUID. Интервалы evidence лежат внутри указанных сегментов. Для ответственного используется пара nullable-полей `assignee_speaker_id`/`assignee_name`: голос либо внешнее имя/подразделение, оба null при неизвестном ответственном; одновременно заполнять оба нельзя. `due_date_text` сохраняет исходную формулировку срока. `identity_status` различает непроверенный голос (`unreviewed`), имя (`named`) и явно подтверждённую неизвестность (`unknown`). Исходный bundle неизменяем; review повышает ревизию, но не меняет исходный result_hash.

## Граница безопасности

Данные встречи перемещаются внутри инфраструктуры команды по защищённому соединению приложение ↔ NVIDIA. Доступ к GPU API только серверный; сторонние AI-провайдеры и отправка содержимого в телеметрию исключены. Supabase Auth/profile остаётся сетевой зависимостью и не хранит содержимое встреч. Поэтому требование о закрытом контуре относится к содержимому встречи; полностью автономная аутентификация не заявляется.

## Возможность записи на сайте

Будущая кнопка записи с разрешения пользователя создаёт файл и передаёт его в тот же pipeline после остановки. Источник browser_recording заменяет uploaded_audio; модели, результаты и дашборд переиспользуются. Подключение к митингу и streaming-анализ до завершения записи являются последующими задачами.

## Проверка при реализации

Проверить реальную обработку контрольного аудио; evidence/спикеров/поручения; сохранение при перезапуске; timeout без дублирования; ACK только после сохранения; очистку обеих временных копий; TTL и повторную загрузку; чтение дашборда и создание PDF из локального результата при недоступном GPU. Подготовленный пример явно маркируется и не заменяет проверку реального ML.
