# Технические требования: Hackalem Meeting Intelligence MVP

## 1. Цель и границы

MVP позволяет авторизованному пользователю загрузить запись встречи, получить расшифровку и структурированные выводы локальной ML-обработки, проверить и исправить результат, подтвердить его и скачать PDF. Основной сценарий асинхронный: после загрузки пользователь видит состояние задачи и возвращается к результату после обработки. Исходная запись и все результаты принадлежат только загрузившему пользователю.

База проекта уже содержит Next.js 16, FastAPI, Supabase Auth, защищённый `/api/v1/me` и таблицу `profiles`. Supabase остаётся источником идентификации и профиля; записи, задачи и артефакты встреч в Supabase не сохраняются. Это целевая спецификация MVP, а не утверждение, что перечисленные ниже функции уже реализованы. Точные поля запросов и ответов задаёт [API_CONTRACT.md](API_CONTRACT.md).

### Входит в MVP

- Загрузка готового аудиофайла через FastAPI с проверкой формата и лимитов.
- Надёжное локальное сохранение исходника и файлового манифеста задачи.
- Один отдельный локальный worker, который опрашивает манифесты и вызывает версионированные локальные ML-адаптеры команды Erasyl.
- Расшифровка, разделение по говорящим при наличии поддержки модели, выводы и цитаты с привязкой ко времени.
- Просмотр и редактирование проекта результата, подтверждение человеком и создание PDF только после подтверждения.
- Просмотр списка, состояния и результатов собственных встреч; повтор обработки при устранимой ошибке и удаление встречи.

### Не входит в MVP

- Внешние AI API, облачное хранение meeting data, Redis, очередь или база данных для встреч.
- Docker как обязательное условие локальной разработки.
- Потоковая публикация частичных ML-результатов, живые подсказки во время разговора и синхронизация встреч между несколькими хостами.
- Автоматическое утверждение выводов, совместный доступ, биллинг и административная аналитика по содержимому записей.

## 2. Пользовательские сценарии и правила

1. Пользователь входит через существующий Supabase Auth и загружает допустимый файл с `metadata` (название, дата, часовой пояс, участники, подтверждение уведомления о записи, необязательная языковая подсказка). API возвращает `meeting_id` и `queued` только после атомарного сохранения исходника и манифеста.
2. Пользователь открывает список и карточку встречи. Интерфейс показывает `status`, `stage`, безопасное сообщение об ошибке и время обновления; пока идёт обработка, он опрашивает API с ограниченной частотой.
3. Worker подготавливает файл, выполняет распознавание, разделение говорящих и анализ; промежуточные артефакты не выдаются как окончательные.
4. После завершения анализа пользователь видит `review_required`, сверяет текст и выводы с записью, называет обнаруженных спикеров, редактирует проект результата и утверждает конкретную ревизию. Пункты саммари и поручений обязаны ссылаться на реальные сегменты.
5. Подтверждение переводит встречу в `approved`. Отдельный запрос экспорта синхронно формирует и кэширует PDF из утверждённой ревизии; при ошибке экспорта подтверждение сохраняется, запрос можно повторить. Новая правка утверждённой встречи удаляет кэш PDF и возвращает `review_required`.
6. Пользователь удаляет встречу и все локальные артефакты. Повторный запрос на удаление безопасен.

Человек несёт окончательное решение о корректности итогового отчёта. Выводы ML отображаются как предложения для проверки; интерфейс не представляет их достоверными без подтверждения. Недостаточное качество записи, отсутствие речи или неподдерживаемый язык должны завершаться понятной ошибкой либо отмеченным неполным результатом, а не выдуманными фактами.

## 3. Технические ограничения и зависимости

| Область | Требование |
| --- | --- |
| Runtime | Существующие Next.js 16 и FastAPI/Python 3.12; один API-процесс и один worker-процесс с общим постоянным локальным каталогом данных. |
| Идентификация | Существующая проверка Supabase JWT; `sub` токена является `owner_id`. Таблица `profiles` остаётся в Supabase. |
| Meeting data | Только файловая система под конфигурируемым `DATA_ROOT`, по умолчанию `data/` вне Git; ни Postgres, ни Supabase Storage для встреч. |
| ML | Локальные веса и адаптеры Erasyl; подготовка медиа может использовать установленный FFmpeg. Внешние сетевые AI-вызовы запрещены. |
| Запуск | Локально без Docker; API, worker и frontend запускаются отдельными командами или dev-скриптом. |
| Развёртывание | Один хост или общая надёжная POSIX-совместимая файловая система для API и worker. Масштабирование на несколько хостов не входит в MVP. |

До включения загрузки `data/` должен быть добавлен в `.gitignore`, каталог должен создаваться с правами только для сервисного пользователя. Исходный файл никогда не помещается в `frontend/public`, Git, журналы или Supabase. При отсутствии необходимых локальных весов система сообщает о недоступности обработки до приёма новых задач либо оставляет очередь с явным состоянием инфраструктуры; она не создаёт фиктивные результаты.

## 4. Функциональные требования и API

Все маршруты, кроме существующего `/health`, требуют `Authorization: Bearer <Supabase access token>`. Владелец определяется исключительно из проверенного токена, а не из параметра запроса. JSON-ответы версионируются через `/api/v1`.

| Маршрут | Назначение и контракт |
| --- | --- |
| `POST /api/v1/meetings` | Multipart upload: аудио `audio` и обязательный JSON `metadata` с `title`, `meeting_date`, `timezone`, `participants[]`, `recording_notice_confirmed=true`, необязательным `language_hint`; `202` с объектом встречи, `status=queued`, `stage=null`. Повторная загрузка создаёт новую встречу; клиент не должен автоматически повторять запрос после неопределённого исхода. |
| `GET /api/v1/meetings` | Список только своих встреч, пагинация по устойчивому курсору и времени создания, без полного текста и бинарных данных. |
| `GET /api/v1/meetings/{id}` | Метаданные, статус, этап, доступные артефакты, публичный код ошибки и версия схемы. Чужой `id` не раскрывается (`404`). |
| `GET /api/v1/meetings/{id}/transcript` | Расшифровка JSON после завершения обработки; `409`, если результат ещё не готов. TXT остаётся внутренним артефактом. |
| `GET /api/v1/meetings/{id}/insights` | Машинные выводы после завершения анализа. |
| `PUT /api/v1/meetings/{id}/review` | Полная замена пользовательских правок при `review_required` или `approved`; `base_revision` предотвращает потерю параллельных правок, конфликт — `409`. Правка утверждённой версии сбрасывает approval и кэш PDF. |
| `POST /api/v1/meetings/{id}/approve` | Подтверждение указанной ревизии; сохраняет авторство и время, переводит в `approved`. |
| `GET /api/v1/meetings/{id}/export.pdf` | Синхронное создание или скачивание кэшированного PDF только в `approved`; `Content-Disposition: attachment`, приватный HTTP-ответ без кеширования. |
| `POST /api/v1/meetings/{id}/retry` | Повтор неудачной обработки из `failed` с тем же исходником; не создаёт вторую встречу. |
| `DELETE /api/v1/meetings/{id}` | Удаление своей встречи и артефактов; во время обработки сначала запрещает новые записи и прекращает/игнорирует работу по этой задаче. |

Форма доменной ошибки — `{"detail": "...", "code": "..."}`; существующие маршруты авторизации сохраняют текущую форму FastAPI с `detail`. Публичный `code` стабилен и не содержит текст записи, абсолютный путь, стек или токен. `401` — неверная сессия, `404` — отсутствующий или чужой ресурс, `409` — конфликт состояния/ревизии или неготовый результат, `413` — превышен размер, `415` — неподдерживаемый формат, `422` — неверные поля, `503` — недоступна очередь/экспорт, `507` — нет места. Клиент может безопасно повторять `GET` для состояния; при неопределённом ответе upload проверяет список встреч перед новой попыткой.

## 5. Модель состояния и данных

Статусы встречи: `queued`, `processing`, `review_required`, `approved`, `failed`. `stage` равен `ingesting`, `transcribing`, `diarizing` или `analyzing` только при `processing`; `exporting` возможен после подтверждения при `approved` во время создания PDF; иначе `stage=null`. Правка `approved` возвращает `review_required`. При пропуске diarization из-за возможностей модели этот этап фиксируется как пропущенный в манифесте, а не подменяется результатом. Допустимые переходы и восстановление описаны в [ARCHITECTURE.md](ARCHITECTURE.md).

Основные сущности: `Meeting` (UUID, owner UUID, название, дата, часовой пояс, участники, факт уведомления, источник, времена, статус/этап, версии), `RecordingRef` (тип источника и ссылка на локальный исходник), `Job` (этап, попытка, heartbeat и код ошибки), `Transcript` (сегменты и временные интервалы), `Insights` (резюме, решения, задачи, ссылки на сегменты), `Review` (редактируемая ревизия и подтверждение), `Report` (PDF и версия исходной ревизии). Схемы JSON содержат `schema_version` и версии моделей для воспроизводимости. Машинные результаты не изменяются после публикации; правки пользователя сохраняются отдельно в `review.json`.

## 6. Нефункциональные требования

- **Целостность:** после ответа `202` исходник и манифест переживают перезапуск процесса. Смена статуса и публикация каждого JSON/PDF выполняются через временный файл и атомарную замену на том же томе; оборванная временная запись не считается результатом.
- **Восстановление:** после внезапной остановки worker обнаруживает незавершённые задачи и повторяет этап без потери исходника или подтверждённых правок. Повторная обработка не публикует частичный PDF и не дублирует встречу.
- **Изоляция:** межпользовательский доступ через API, обход каталога, symlink-атаки и подмена имени файла исключены проверкой JWT, серверными UUID, канонизацией путей и безопасным открытием файлов. У worker нет Supabase service-role key.
- **Ограничения:** конфигурируемые пределы размера, длительности, одновременных задач и свободного места проверяются до и в ходе загрузки. Начальные значения для локального MVP: до 100 MiB на файл и один активный ML-job. Допустимые форматы: `.wav`, `.mp3`, `.m4a`, `.ogg`, `.webm` с проверкой содержимого. Максимальную длительность определяют характеристики локальной модели и задают конфигурацией до запуска.
- **Доступность интерфейса:** загрузка быстро получает ответ после записи файла; ML работает вне HTTP-запроса. UI различает очередь, обработку, проверку, готовность и ошибку, поддерживает клавиатуру и не полагается только на цвет.
- **Производительность:** целевое время появления новой задачи у worker — до 5 секунд при здоровом локальном окружении. Время расшифровки зависит от длительности записи и оборудования; честно отображаются этап и ожидание, без обещания фиксированного SLA обработки.
- **Наблюдаемость:** структурированные журналы по `request_id`, `meeting_id`, этапу, длительности и кодам ошибок, без содержимого записи и персональных токенов; `/health` проверяет процесс API, отдельная readiness-проверка отражает доступность хранилища и worker.
- **Хранение:** исходники и результаты удаляются по запросу владельца; политика автоочистки задаётся конфигурацией и показывается пользователю. По умолчанию автоматического удаления нет, пока UI не объясняет срок хранения. Резервное копирование и очистка проверяются на тестовых данных.

## 7. Этапы поставки и Definition of Done

| Этап | Результат |
| --- | --- |
| 1. Основа | Схемы артефактов, безопасное локальное хранилище, upload/list/detail API, проверка владельца, лимиты, игнорирование `data/` Git. |
| 2. Обработка | Отдельный worker, восстановление после перезапуска, локальные ML-адаптеры Erasyl, расшифровка и выводы с версиями и ссылками на исходные сегменты. |
| 3. Проверка и экспорт | UI просмотра/редактирования, конкурентные ревизии, явное подтверждение, PDF только из подтверждённой ревизии. |
| 4. Завершение | Повторы и удаление, диагностические статусы, документация запуска и проверка полного пользовательского пути. |

MVP принят, когда пользователь может пройти путь «вход → загрузка → ожидание → просмотр → правка → подтверждение → PDF → удаление» на чистой локальной установке без Docker и внешнего AI API; два разных пользователя не могут прочитать или изменить данные друг друга; прерывание worker между этапами не теряет запись и не выдаёт неполный отчёт; PDF до подтверждения недоступен. Автоматические тесты покрывают авторизацию, лимиты, схемы, переходы состояния, сбои/повторы, атомарность и ownership; интеграционный тест использует локальные тестовые адаптеры, а ручной smoke test — реальную модель и короткую контрольную запись. Для демо без готовой реальной модели допускается только заранее рассчитанный результат для конкретной контрольной записи с заметной меткой `demo_fixture`; произвольные загрузки не получают фиктивный результат. Проверки существующего frontend/backend starter продолжают проходить.

## 8. Эволюция после MVP

Живой источник в будущем передаёт завершённую запись как тот же `RecordingRef`, после чего запускается тот же конвейер. Этот контракт даёт возможность заменить способ получения медиа без изменения анализа и review. Захват живого аудио, согласие участников, сетевое соединение и частичные подсказки требуют отдельного проектирования; текущий MVP не обещает анализ во время встречи. При переходе к нескольким worker или хостам файловый манифест и локальное владение заменяются транзакционной очередью и общей системой хранения с миграцией существующих артефактов и сохранением API-контрактов.
