# Технические требования: Hackalem Meeting Intelligence MVP

## 1. Цель и статус

Целевая схема: сайт загружает аудио или видео → FastAPI приложения локально проверяет контейнер и при необходимости извлекает первую аудиодорожку → выделенный NVIDIA-сервер команды с собственной моделью получает только аудио → результаты сохраняются локально на стороне приложения → дашборд, проверка и PDF. Исходное staged-видео удаляется сразу после успешного извлечения, временное аудио — после подтверждения сохранения результатов.

Под локальным хранением результатов понимается диск backend приложения (`data/`), а не браузер или GPU-сервер. Это рабочее допущение. Архитектурные детали — в [ARCHITECTURE.md](ARCHITECTURE.md), схемы — в [API_CONTRACT.md](API_CONTRACT.md).

## 2. Обязательные функции

- Загрузка аудио или видео с названием, датой, часовым поясом, участниками и подтверждением уведомления о записи; для видео локально извлекается первая аудиодорожка.
- Передача на NVIDIA по защищённому аутентифицированному каналу; модель работает на сервере команды без внешних AI API.
- Русский, казахский и смешанная речь, транскрипт с таймкодами и диаризацией.
- Саммари, поручения, ответственные и сроки с evidence-ссылками; неопределённые значения не выдумываются.
- Сохранение JSON/TXT и правок на стороне приложения; отображение в дашборде.
- Правки, утверждение человеком и PDF из сохранённой утверждённой версии.
- Подтверждаемая очистка временного аудио и производных медиа на GPU и в приложении.

## 3. Runtime и границы

| Область | Требование |
| --- | --- |
| Приложение | Next.js 16 + FastAPI/Python 3.12; локальные `ffprobe`/`ffmpeg` проверяют загрузку и извлекают аудио из видео с жёстким timeout; лёгкий coordinator возобновляет передачу и получение GPU-задач по локальным manifests. |
| GPU | Выделенный NVIDIA-сервер: inference API, один worker и собственные модели Erasyl. |
| Данные | Результаты в DATA_ROOT приложения, временные GPU-данные в GPU_TEMP_ROOT; общий диск не нужен. |
| Auth | Существующий Supabase JWT определяет владельца. GPU API использует отдельный серверный credential, не пользовательский JWT. |
| Инфраструктура | Без Docker, Redis и БД встреч. Сетевой доступ приложение ↔ NVIDIA обязателен для обработки. |
| Будущее | Запись на сайте отправляет готовый файл по тому же пути. Конференц-боты и streaming-анализ позже. |

Supabase Auth/profile пока остаётся сетевой зависимостью; содержимое встречи туда не передаётся. Сохранённые результаты доступны без GPU, но доступ к интерфейсу по-прежнему зависит от действующей аутентификации.

## 4. HTTP и данные

Публичные routes и авторизация остаются на FastAPI приложения. Клиент не видит адреса временных файлов или credential NVIDIA-сервиса. Meeting endpoints реализованы; настоящий NVIDIA worker подключается через описанный внутренний контракт.

| Маршрут | Назначение |
| --- | --- |
| POST /api/v1/meetings | Multipart media в совместимой части `audio` + metadata; видео нормализуется локально в audio-only M4A, после сохранения временного аудио и manifest возвращается 202 queued. |
| GET /api/v1/meetings | Собственные встречи, пагинация. |
| GET /api/v1/meetings/{id} | Статус, этап, доступность исходника и cleanup_status. |
| GET /api/v1/meetings/{id}/transcript | Сохранённый транскрипт JSON. |
| GET /api/v1/meetings/{id}/insights | Сохранённые саммари и поручения. |
| PUT /api/v1/meetings/{id}/review | Сохранение правок с base_revision; новая правка снимает approval и инвалидирует PDF. |
| POST /api/v1/meetings/{id}/approve | Утверждение текущей ревизии человеком. |
| GET /api/v1/meetings/{id}/export.pdf | Синхронное создание/кэш PDF из локальных результатов после approval. |
| POST /api/v1/meetings/{id}/retry | Повтор failed только при доступном временном исходнике; иначе 409 source_expired и новая загрузка. |
| DELETE /api/v1/meetings/{id} | Удаление локальных результатов после завершения обработки и GPU-очистки; при активной задаче или cleanup pending — 409. |

Сущности сохраняются: Meeting, RecordingRef, Job, TranscriptV1, InsightsV1, Review, Report. Meeting хранит GPU job ID и номер попытки, результат — версию схемы и модели. Публичные status: queued, processing, review_required, approved, failed. Stage также отражает uploading_to_gpu и saving_results. Cleanup не подменяет статус качества результата: pending, deleted или expired хранится отдельно.

## 5. Надёжность и хранение

- После 202 задача и нормализованный временный audio upload переживают перезапуск API до подтверждённого сохранения результата или TTL. Исходный staged-видеофайл к этому моменту уже удалён.
- Submit GPU использует стабильный ключ meeting_id:attempt. Timeout повторяет запрос к той же задаче, а не запускает дубликат inference.
- Результат валидируется и публикуется локально полностью; manifest отмечает готовность последним. Только затем посылается ACK на GPU.
- ACK идемпотентен; после него удаляются аудио, chunks и временный результат NVIDIA-сервера. Временный upload приложения тоже очищается.
- Предлагаемый TTL временных данных — 24 часа от приёма; cleanup работает и для ошибок, отменённых/брошенных задач, перезапусков. Активный job перед очисткой по TTL останавливается.
- При потере ACK результат остаётся локально, cleanup pending повторяется. Если GPU-данные истекли до получения результата, UI требует повторную загрузку.
- Постоянное архивирование аудио не предусмотрено. Evidence после удаления — цитата, сегмент и таймкод транскрипта.
- Локальные результаты и правки сохраняются до удаления пользователем; старые PDF инвалидируются при правке.
- Весь data/ и GPU_TEMP_ROOT исключён из Git; логирование аудио, транскриптов и секретов запрещено.

## 6. Ограничения и наблюдаемость

Начальные проектные настройки: один GPU-job одновременно, входной файл до 100 MiB; audio-only WAV/MP3/M4A/OGG/WebM передаются без перекодирования после проверки, MP4/MOV/MKV и WebM с видеодорожкой локально преобразуются по первой аудиодорожке в audio-only M4A. `ffprobe` ограничен 5 секундами, `ffmpeg` — 120 секундами и одним потоком; выход также ограничен 100 MiB и повторно проверяется. Ошибка чтения, отсутствие аудиодорожки, timeout или превышение выходного лимита дают безопасный отказ `unsupported_media_type`, не публикуя встречу. Это настраиваемые границы MVP, не измеренные характеристики сервера. Время обработки измеряется на модели Erasyl; SLA и точность заранее не обещаются.

Приложение хранит GPU_API_URL/TOKEN только на backend; канал использует TLS или доверенный VPN/SSH-туннель. API проверяет JWT и owner_id перед чтением локальных артефактов; чужая встреча возвращает 404. Ошибки различают invalid state, source_expired, GPU unavailable, storage failure и cleanup pending, без приватных данных.

Журналы содержат job ID, stage, попытку, время и безопасный код. Health приложения отличается от доступности GPU и модели. UI показывает реальный этап и сетевое ожидание, не выдуманный процент.

## 7. Приёмка и порядок будущей реализации

1. Контракты приложения и GPU, локальное сохранение результатов и upload API.
2. Соединение с NVIDIA, worker модели, получение результата и возобновление после сетевого сбоя.
3. Дашборд, review, approval и PDF.
4. ACK/TTL-очистка, обработка ошибок и end-to-end demo.

Обязательные проверки: реальная RU/KK/mixed запись; связывание поручений с цитатами; ownership; обрыв сети без дублей; сбой диска до ACK; повтор ACK; удаление временных данных на обеих машинах; истечение TTL; результаты/PDF после отключения GPU. Подготовленный demo_fixture явно маркируется и не доказывает работу реального STT.

Все функции выше — требования к будущим задачам; этот документ не вводит runtime-код или настройки.
