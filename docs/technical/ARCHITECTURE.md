# Архитектура локального конвейера встреч

## 1. Контекст и принципы

Существующий поток аутентификации остаётся неизменным: Next.js получает Supabase-сессию, браузер посылает access token в FastAPI, FastAPI проверяет JWT. Таблица `profiles` остаётся в Supabase. Для meeting data FastAPI становится единственной точкой доступа к локальному хранилищу, поскольку Supabase RLS не защищает файлы на диске. Владелец каждой встречи — UUID из `sub` проверенного JWT. Ни frontend, ни клиентский код не получают прямой путь к файлу. Точные внешние JSON-схемы и коды HTTP определены в [API_CONTRACT.md](API_CONTRACT.md); здесь описан внутренний конвейер.

```text
Browser / Next.js 16 ── Bearer JWT ──> FastAPI ──> DATA_ROOT/users/<owner>/meetings/<id>/
         │                                 │                      ▲
         └──── Supabase Auth/profile ──────┘                      │
                                                 local worker ────┘
                                                      │
                                           versioned local ML adapters
```

API принимает и выдаёт данные, worker выполняет ресурсоёмкую обработку. Оба процесса используют один локальный том. В MVP запускается ровно один worker; файловый манифест является надёжной очередью и источником состояния. JSON и PDF публикуются только целиком. Внешний AI API, Redis и база данных задач отсутствуют.

## 2. Границы модулей

| Модуль | Ответственность | Зависимости |
| --- | --- | --- |
| `api/routes/meetings` | HTTP-контракт, multipart, авторизация, коды ошибок, условное обновление review. | Существующий `get_current_user`, прикладной сервис. |
| `services/meetings` | Правила состояний, ownership, идемпотентность, ревизии, удаление. | Репозиторий и порт обработки. |
| `storage` | Безопасные пути, потоковая запись, атомарные файлы, чтение манифестов, очистка. | Локальная файловая система. |
| `worker` | Опрос очереди, восстановление, ограничение параллелизма, запуск стадий и heartbeat. | Репозиторий и ML-порты. |
| `ml/adapters` | Версионированные локальные реализации ASR, diarization, анализа. | Модели/веса Erasyl, локальный медиадекодер. |
| `reporting` | Синхронный PDF-экспорт по защищённому GET только из утверждённой ревизии, кэш по её номеру, запись хеша/версии. | Локальный рендерер и шрифты. |
| Frontend | Загрузка, статусы, просмотр и редактирование, подтверждение, скачивание. | API-клиент и существующая Supabase-сессия. |

HTTP-слой не импортирует конкретную ML-модель. ML-адаптеры не знают о JWT, HTTP и структуре каталогов пользователя: им передают подготовленный `RecordingRef` и временные пути, а возвращаемые объекты валидируются общей схемой. Это позволяет заменить модели без изменения API и сравнивать результаты по `adapter_version`/`model_version`.

## 3. Доменная модель и схемы артефактов

`Meeting` содержит `id: UUID`, `owner_id: UUID`, `title`, `meeting_date`, `timezone`, `participants[]`, `recording_notice_confirmed`, `language_hint`, `created_at`, `updated_at`, `status`, `stage`, `schema_version`, `recording`, `job`, `artifact_versions`, `failure`. `RecordingRef` содержит `kind` (`uploaded_audio` сейчас; `live_capture` в будущем), `object_key` внутри каталога встречи, оригинальное отображаемое имя, MIME, размер, SHA-256 и длительность после probe. `object_key` не является абсолютным или клиентским путём. Отдельный `demo_fixture` допустим только для заранее подготовленного демонстрационного аудио и явно обозначается пользователю. `Job` содержит `attempt`, `worker_id`, `started_at`, `heartbeat_at`, `retry_after`, `last_completed_stage`, машинный `error_code` и признак возможности повтора.

`Transcript` содержит версию схемы, язык, список `segments` с устойчивым `segment_id`, `start_ms`, `end_ms`, `text`, необязательными `speaker_id` и `confidence`, а также версии ASR и diarization. Временные интервалы не пересекают длительность записи; пустая речь — валидный диагностический результат, а не повод сочинять текст. `Insights` содержит краткое резюме, решения, задачи (`description`, необязательные `assignee`/`due_date`), ключевые тезисы и ссылки на существующие `segment_id`; недоказанные имена и сроки остаются `null`. Анализ не принимает свободный путь к записи и не изменяет исходный transcript.

`Review` создаётся копированием машинных результатов, содержит `revision` (монотонный номер), имена спикеров, отредактированные сегменты/выводы, `edited_at`, `approved_revision`, `approved_by`, `approved_at`. Правки сохраняют provenance исходных сегментов, а произвольные новые заметки маркируются как пользовательские. После подтверждения эта ревизия неизменна; повторный экспорт читает именно её. `Report` содержит PDF, `source_review_revision`, SHA-256, время и версию шаблона. В каждом JSON есть `schema_version`; чтение неизвестной версии завершается явной ошибкой миграции, а не молчаливым приведением.

Рекомендуемая структура одного каталога:

```text
DATA_ROOT/
  users/<owner_uuid>/meetings/<meeting_uuid>/
    meeting.json
    audio/original.<validated_extension>
    transcript.json
    transcript.txt
    insights.json
    review.json
    exports/protocol.pdf
    tmp/
```

Отсутствующий артефакт означает, что стадия ещё не завершена; `meeting.json` является манифестом и перечисляет опубликованные файлы, их хеши, версии и состояние. `tmp/` хранит только временные файлы, которые можно удалить при восстановлении. Имена, переданные пользователем, записываются лишь как очищенные метаданные и никогда не участвуют в построении пути. Идемпотентность в MVP относится к этапам worker и PDF для пары `(meeting_id, revision)`; повторная загрузка создаёт отдельную встречу.

## 4. Загрузка и атомарность

API проверяет JWT, обязательный JSON `metadata` (включая `recording_notice_confirmed=true`), квоту пользователя, свободное место и тип содержимого, затем потоково записывает файл в уникальный временный каталог на том же томе, одновременно считает SHA-256 и размер. Ограничение размера применяется во время чтения потока; MIME заголовка не считается доказательством формата. После media probe валидируются длительность, контейнер и возможность декодирования. Ошибочная загрузка удаляет временный файл и не появляется в списке.

Для принятого файла API создаёт серверный UUID, перемещает исходник в каталог встречи, записывает `meeting.json` через временный файл, `fsync` файла и каталога, затем атомарную замену. Ответ `202` отправляется после публикации манифеста. Крах до публикации оставляет только осиротевший временный каталог, который уборщик удалит; крах после публикации оставляет `queued`, который увидит worker. Клиент не повторяет автоматически upload после неопределённого исхода: сначала сверяет список собственных встреч.

Любое обновление JSON/PDF проходит валидацию, запись во временный файл в том же каталоге, `fsync`, атомарную замену и публикацию ссылки/хеша в манифесте. Читатель доверяет только артефактам, указанным в манифесте с подходящей версией. При сбое между созданием файла и обновлением манифеста лишний файл не считается готовым и может быть повторно создан. На локальном файловом томе, не поддерживающем требуемую атомарность, запуск блокируется диагностикой.

## 5. Состояния, работа worker и восстановление

| Из | В | Условие |
| --- | --- | --- |
| Создание | `queued`, `stage=null` | Исходник и манифест опубликованы. |
| `queued` | `processing`, `stage=ingesting` | Worker взял задачу. |
| `processing` | `processing` со стадиями `transcribing`, `diarizing`, `analyzing` | Предыдущая стадия завершилась и её артефакт опубликован. |
| `processing`, `stage=analyzing` | `review_required`, `stage=null` | Transcript, insights и начальная review-ревизия валидны и опубликованы. |
| `review_required` | `approved`, `stage=null` | Владелец подтвердил конкретную review-ревизию. |
| `approved`, `stage=null` | `approved`, `stage=exporting`, затем `stage=null` | Защищённый GET синхронно создаёт и кэширует PDF из подтверждённой ревизии; статус не меняется. |
| `approved`, `stage=null` | `review_required`, `stage=null` | Владелец сохраняет новую ревизию review; approval и PDF-кэш инвалидируются. |
| `queued` или `processing` | `failed`, `stage=null` | Постоянная ошибка или исчерпаны попытки; код и этап сохранены. |
| `failed` | `queued` | Явный retry обработки после исправления условия. Ошибка PDF не переводит встречу в `failed`; повторяют `GET /export.pdf`. |

В MVP только один worker опрашивает манифесты, выбирая ожидающие задачи по времени создания; отдельная распределённая блокировка не нужна. Он записывает `worker_id`, `attempt` и `heartbeat_at`, затем выполняет стадию. При старте worker сканирует `queued` и `processing` с устаревшим heartbeat. Стадия возобновляется с последнего опубликованного валидного артефакта; незавершённые временные файлы удаляются. PDF создаётся отдельно по защищённому HTTP-запросу после approval. Для защиты от случайного запуска второго worker процесс берёт эксклюзивный локальный lock на `DATA_ROOT`; второй экземпляр завершается с понятной ошибкой. Это предохранитель одного хоста, а не распределённый claim-протокол.

Каждая стадия проверяет входной хеш и версии адаптеров. Повторный запуск с теми же входом и версиями может переиспользовать опубликованный артефакт; при изменении версии создаётся новая попытка с явным обновлением версии, а review-правки не перезаписываются автоматически. Временная ошибка получает ограниченный exponential backoff и максимум попыток из конфигурации; недопустимый формат, отсутствие речи для требуемого сценария и нарушенная схема считаются постоянными. Worker не читает Supabase и не хранит пользовательский токен. Если встреча удаляется во время стадии, API помечает tombstone; worker прекращает публикацию, после чего каталог удаляется безопасно. После окончательного удаления API отвечает `404`.

`ingesting` выполняет окончательный probe/нормализацию. `transcribing` создаёт transcript. `diarizing` добавляет speaker labels, если адаптер поддерживает задачу; иначе это явно отмеченный пропуск. `analyzing` создаёт insights и review-черновик. `exporting` выполняется синхронно в API после сохранения `approved_revision` по запросу владельца и строит PDF. При одновременных запросах локальная блокировка для пары `(meeting_id, revision)` не допускает двойного экспорта. При новой правке PDF-кэш инвалидируется и требуется повторное подтверждение. Клиенту не выдаются частичные выводы как утверждённый отчёт.

## 6. Контракты локальных ML-портов

Три логических порта: `Transcriber.transcribe(recording, context) -> Transcript`, `Diarizer.assign_speakers(recording, transcript, context) -> Transcript`, `Analyzer.analyze(transcript, context) -> Insights`. Каждый адаптер предоставляет `adapter_name`, `adapter_version`, `model_version`, поддерживаемые языки/форматы и локальную проверку готовности. `context` содержит идентификатор попытки, отмену, ресурсные лимиты и временный рабочий каталог, но не JWT. Результат проходит Pydantic/JSON Schema валидацию до публикации: корректные интервалы, непустые идентификаторы, конечные числовые значения, ссылки insights только на существующие сегменты.

Ошибки делятся на `unsupported_media`, `unsupported_language`, `no_speech`, `model_unavailable`, `resource_exhausted`, `decode_failed`, `transient_processing_error` и `invalid_model_output`. Адаптер обязан сообщать машинный код и диагностический текст для приватного журнала; API выдаёт безопасное описание. Тестовый адаптер детерминирован и работает без скачивания весов; production adapter Erasyl подставляется конфигурацией. Отдельный demo adapter разрешён только для заранее известного аудио и помечает результат `demo_fixture`. Ни один адаптер не отправляет аудио, текст или эмбеддинги во внешнюю сеть. Начальная версия контракта фиксируется как `schema_version=1`, изменение несовместимого формата требует новой версии и явного мигратора или повторной обработки.

## 7. Безопасность, срок хранения и ошибки

Для каждого запроса API сначала проверяет JWT, затем находит встречу только внутри каталога `owner_id` из токена. UUID валидируются до обращения к диску. Символические ссылки внутри дерева запрещены, файлы открываются с защитой от следования по ссылкам, путь после разрешения остаётся внутри `DATA_ROOT`. Права каталога ограничены сервисным пользователем; PDF и исходник выдаются с `Cache-Control: private, no-store`. CORS ограничен адресом frontend из настройки. Пользовательские названия, transcript и токены не пишутся в обычный лог.

Временные каталоги старше заданного периода и осиротевшие артефакты удаляются отдельной безопасной уборкой. Удаление встречи по API прекращает публикацию и удаляет исходник, JSON и PDF; резервные копии, если они включены администратором, имеют отдельный документированный срок. Начальная политика автоматического удаления — выключена, пока пользовательский интерфейс явно не показывает срок. Для первого релиза следует указать локальный `DATA_ROOT` в политике конфиденциальности продукта и получить согласие на обработку записи по правилам команды.

Отказ диска, нехватка места, повреждённый манифест и недоступная модель приводят к машинному коду, сохраняемому в манифесте, и операционному сигналу. Повреждённый манифест не перезаписывается пустым объектом: файл изолируется для диагностики, задача не показывается как успешная. При ошибке экспорта `approved_revision` остаётся сохранённой, так что повтор не требует нового подтверждения. Внешняя ошибка Supabase влияет на новые авторизованные HTTP-запросы, но worker продолжает уже принятые локальные задания.

## 8. Конфигурация и процессы

Новые backend-настройки: `DATA_ROOT`, `MAX_UPLOAD_MIB`, `MAX_RECORDING_MINUTES`, `MAX_ACTIVE_JOBS_PER_USER`, `MIN_FREE_DISK_MIB`, `WORKER_POLL_SECONDS`, `WORKER_HEARTBEAT_SECONDS`, `WORKER_MAX_ATTEMPTS`, `WORKER_RETRY_BASE_SECONDS`, `ML_ADAPTER`, `MODEL_DIR`, `FFMPEG_PATH`, `REPORT_TEMPLATE_VERSION`, `TEMP_RETENTION_HOURS`, `MEETING_RETENTION_DAYS` (пустое значение отключает автоудаление). Секреты Supabase берутся из существующих настроек; worker их не требует. Конфигурация валидируется при старте, а абсолютный `DATA_ROOT` и доступность модели проверяются readiness-проверкой.

Локальный запуск: настроить существующие env-файлы для Supabase Auth; установить Python/Node зависимости, FFmpeg и локальные веса; запустить FastAPI, worker и Next.js отдельными процессами. Docker не нужен. Тестовый режим использует временный `DATA_ROOT` и тестовые адаптеры. Продакшен MVP размещает API и worker на одном постоянном томе одного хоста; ephemeral filesystem платформы без подключённого постоянного тома непригодна. Worker перезапускается менеджером процессов, а graceful shutdown завершает текущую атомарную запись и оставляет незавершённую стадию для восстановления.

## 9. Наблюдаемость, тесты и развитие

Структурированный лог содержит `request_id`, `meeting_id`, `owner_id` в сокращённом/хешированном виде, `stage`, `attempt`, длительность и `error_code`; содержимое встречи не логируется. Измеряются длина очереди, возраст старейшей задачи, время по стадиям, число retry, ошибки схемы, использование диска и возраст heartbeat. `/health` отвечает за живость API; readiness сообщает отдельно о доступности `DATA_ROOT`, worker heartbeat и моделей, чтобы отсутствие worker не скрывалось за успешным HTTP health.

Тесты слоя storage проверяют атомарную публикацию манифестов, обрыв загрузки и дисковую ошибку; тесты state machine — все допустимые и запрещённые переходы, повторное подтверждение и retry экспорта; API-тесты — два владельца, обход пути, размер/тип файла, ревизионный конфликт и отсутствие PDF до утверждения; worker-тесты — перезапуск на каждой стадии с детерминированным адаптером. Контрактные тесты Erasyl адаптеров проверяют версии и схемы на небольшой контрольной записи. Полный локальный smoke test проходит от загрузки до PDF с реальной моделью и проверяет, что PDF соответствует утверждённой ревизии.

Будущий live capture должен после завершения захвата создать тот же `RecordingRef` с `kind=live_capture` и локальным `object_key`, затем пройти неизменённые стадии и review. При необходимости анализа до завершения записи понадобятся отдельные протоколы событий, согласие участников, обработка прерываний и семантика частичных результатов. Миграция на несколько worker потребует транзакционной очереди, lease/fencing и общего хранилища; локальный lock и сканирование файлов предназначены только для одного хоста MVP.
