# Архитектура обработки на NVIDIA-сервере

## 1. Уточнение архитектуры

Статус: проектирование, функции встреч ещё не реализованы. Согласованная с пользователем схема заменяет прежнее предположение об ML на машине приложения: модель запускается на выданном команде NVIDIA-сервере. Постоянные результаты хранятся локально на стороне приложения; аудиозаписи сервера временные.

Под локальным хранением результатов пока понимается `data/` на машине backend приложения, а не браузерное хранилище. Продуктовый flow и экраны описаны в [PRD](../product/PRD.md), публичный интерфейс — в [API_CONTRACT](API_CONTRACT.md).

```text
Сайт Next.js: загрузка файла / позже запись в браузере
    ↓
FastAPI приложения: проверка доступа, временный upload
    ↓ защищённый запрос с service credential
NVIDIA-сервер команды: inference API + worker + собственная модель
    ↓ транскрипт, спикеры, саммари, поручения и источники
FastAPI: проверка результата → сохранение в data/ → дашборд
    ↓ подтверждение сохранения
NVIDIA-сервер: удаление временного аудио и результатов
Приложение: удаление временной upload-копии
```

Обычный Python-worker работает на NVIDIA-сервере и обрабатывает одну задачу за раз. Next.js и FastAPI приложения запускаются отдельно. Docker, Redis и БД встреч для MVP не нужны; общая файловая система между этими двумя машинами тоже не нужна.

## 2. Границы модулей

| Компонент | Ответственность |
| --- | --- |
| Next.js | Загрузка, прогресс, дашборд саммари/поручений/транскрипта, исправления, утверждение и PDF. |
| FastAPI приложения | Supabase JWT, ownership, HTTP-контракт, приём файла, review и PDF. |
| GPU client / coordinator | Отправка задачи, сохранение job ID, опрос, получение и валидация результата, подтверждение сохранения и повтор очистки. Это лёгкая возобновляемая фоновая работа внутри API, без локальной ML-модели. |
| LocalArtifactStore | Локальные JSON/TXT, машинный результат и пользовательские правки, атомарная публикация. |
| NVIDIA inference API | Доступ только backend приложения по серверному credential; временные задания, получение результата и подтверждение очистки. |
| NVIDIA worker / ML adapters | ASR, диаризация, анализ; локальные веса, без сторонних AI API. |
| Cleanup на обеих машинах | Удаление временных данных после получения результата и по TTL, обработка неудачных/брошенных задач. |

Схемы результатов версионируются: `TranscriptV1`, `InsightsV1` (`schema_version: 1`), внутри `ResultBundleV1` с `model_versions` и SHA-256 `result_hash`. Точный состав и каноническая сериализация — в [API_CONTRACT](API_CONTRACT.md). Голоса имеют стабильные метки `speaker_N`, сегменты/пункты — UUID; evidence ограничен границами своего сегмента. Nullable `assignee_name` задаёт внешнего ответственного, только при `assignee_speaker_id: null`; оба null означают неизвестность. `due_date_text` сохраняет исходный срок. ML-порты остаются внутри NVIDIA-сервиса: Transcriber, Diarizer, Analyzer. API/UI не зависят от выбранных моделей. GPU-сервис получает контекст даты и участников, но не пользовательский JWT.

## 3. Хранение и срок жизни

На стороне приложения:

```text
data/users/<owner_uuid>/meetings/<meeting_uuid>/
  meeting.json
  transcript.json
  transcript.txt
  insights.json
  review.json
  exports/protocol.pdf
  tmp/upload.<validated_extension>  # только до сохранения результата или TTL
```

На NVIDIA-сервере:

```text
GPU_TEMP_ROOT/<job_id>/
  job.json
  audio/
  working/
  result.json
```

Все эти каталоги исключаются из Git. В `meeting.json` сохраняются владелец, дата/часовой пояс, участники, источник, status/stage, job ID, номер попытки, версии схем/моделей, исходный result_hash, признак сохранения результата и `cleanup_status` (`pending|deleted|expired`). UUID и пути хранилища формирует сервер; UUID новых пунктов review создаёт клиент с последующей проверкой сервером.

Начальный TTL — 24 часа от приёма на каждой машине, включая неудачные и брошенные задачи. Повторы submit/poll/result/ACK/retry не продлевают срок существующего upload/job; новая GPU-попытка получает свой deadline. `temporary_expires_at` публичной встречи — срок локального upload, `source_available` требует наличия этого upload и неистёкшего срока. При успешном сохранении очистка выполняется сразу, не дожидаясь TTL. Перед удалением активного задания по TTL сервер останавливает обработку и запрещает публикацию позднего результата. Сбой очистки сохраняется как `pending` и повторяется; факт удаления подтверждается, а не предполагается.

Постоянные результаты на стороне приложения не удаляются вместе с временным аудио; их удаляет владелец встречи. На GPU удаляются исходник, нормализованное аудио, chunks и временный результат. После подтверждённой очистки GPU хранит 7 суток квитанцию без содержимого встречи: job ID, idempotency key/fingerprint, result_hash (или null), status, cleanup_status и сроки. В этом окне повтор ACK проверяет тот же хеш; повтор submit возвращает тот же job без inference, а для expired-задачи — 410 source_expired. После удаления квитанции GET/result/ACK возвращают 404; приложение оставляет cleanup pending для сверки оператором, не объявляет удаление успешным.

## 4. Передача результата без потери данных

1. FastAPI проверяет JWT и metadata, ограничивает размер upload и временно сохраняет аудио плюс manifest; затем отвечает `202 queued`.
2. Coordinator отправляет задачу на GPU с устойчивым idempotency key `meeting_id:attempt`; повтор передачи после timeout возвращает ту же задачу.
3. GPU сохраняет задание, worker исполняет модель; coordinator опрашивает известный job ID. Потеря соединения не означает ошибку самой модели.
4. Backend получает полный результат, проверяет версии, поля и evidence-ссылки. Пишет JSON/TXT через временные файлы и atomic replace, публикует признак готовности последним в manifest.
5. Только после надёжной локальной записи backend отправляет ACK с job ID и хешем результата. GPU надёжно фиксирует принятый хеш и намерение очистки, закрывает выдачу payload, удаляет временные данные и только затем подтверждает cleanup. Backend удаляет свою upload-копию после надёжного сохранения независимо от ответа ACK. Повтор ACK безопасен, даже после частичного удаления; несовпадающий хеш запрещает очистку.
6. UI читает сохранённые результаты из backend. Ошибка ACK/очистки не уничтожает результат: остаётся `cleanup_status=pending` до подтверждённой очистки всех временных копий всех попыток. `deleted` означает очистку до TTL; `expired` — подтверждённое удаление хотя бы одной копии по TTL. Истёкший payload сразу недоступен, но сбой физического удаления сохраняет pending.
7. После перезапуска coordinator восстанавливает передачу/получение/ACK по manifest. При истечении TTL на GPU и отсутствии локального результата задача требует новой загрузки. Если результат уже сохранён, он остаётся доступен.

Запись нескольких файлов сама по себе не является транзакцией: готовность определяется последним опубликованным manifest и хешами артефактов. Недозаписанный результат не переводит встречу в `review_required` и не даёт права отправить ACK.

## 5. Состояния и проверка человеком

Публичные состояния сохраняются: `queued → processing → review_required → approved`; `failed` — окончательная ошибка. Отдельный stage включает `uploading_to_gpu`, `ingesting`, `transcribing`, `diarizing`, `analyzing`, `saving_results` и `exporting`. Ожидание связи показывается отдельно от ошибки модели.

Approval требует проверки каждого голоса: `identity_status: named` с именем либо явно выбранный `unknown` с `display_name: null`. `unreviewed` блокирует approval. Неизвестные ответственный/срок допустимы.

PDF создаётся backend приложения по запросу после approval из локальной review-ревизии. Изменение утверждённого результата возвращает `review_required` и инвалидирует PDF-кэш. После удаления исходного аудио остаются транскрипт, цитаты, ссылки на сегменты и таймкоды; постоянное серверное прослушивание записи не входит в этот flow. Пользователь может повторно выбрать свой исходный файл для прослушивания в браузере в будущем.

Retry вычисления возможен, пока доступен временный исходник. После его удаления API возвращает `409 source_expired`; UI предлагает новую загрузку. Повтор скачивания результата или ACK не расходует попытку ML. Для простоты удаления встречи в MVP операции запрещены при `queued`, `processing` (`409 invalid_state`) или незавершённой очистке (`409 cleanup_pending`); сначала задача/TTL-очистка должна завершиться.

## 6. Доступ и граница данных

Аудио и текст передаются только между приложением и контролируемым командой NVIDIA-сервером. Канал защищён TLS либо доверенным VPN/SSH-туннелем; inference API требует серверный credential, который не попадает в браузер. Модели и веса предварительно размещены на сервере; во время inference содержимое не отправляется сторонним AI-сервисам или в телеметрию.

Supabase остаётся существующим каналом Auth/profile, поэтому текущая схема локализует содержимое встреч, но не делает аутентификацию полностью автономной от сети. Аудио, транскрипты и поручения в Supabase не сохраняются.

Каждый публичный запрос проверяет владельца; чужие UUID дают 404. Папки доступны сервисному пользователю; клиентские имена не формируют пути, symlink/path traversal запрещены. Содержимое встреч не попадает в логи. Удаление временных файлов исключает дальнейшую выдачу через API; криптографическое стирание SSD не заявляется.

## 7. Конфигурация и проверка

Приложение: `DATA_ROOT`, `GPU_API_URL`, `GPU_API_TOKEN`, timeout/poll interval, лимит загрузки (начальное предложение: 100 MiB), `TEMP_RETENTION_HOURS=24`.
NVIDIA-сервис: `GPU_TEMP_ROOT`, локальные модели/`MODEL_DIR`, лимиты ресурсов, тот же TTL, один worker. Значения пока описаны в документах; env-файлы и runtime ещё не изменены.

Проверить при реализации: получение результата при обрыве связи; отсутствие дублирования job; сбой локальной записи запрещает ACK; повтор ACK; восстановление после перезапуска; фактическая очистка обеих временных копий; TTL неуспешных задач; доступ к результату при выключенном GPU; ownership; review/PDF после удаления аудио. На демонстрации требуется реальный RU/KK/mixed sample; заранее подготовленный результат имеет явную метку demo_fixture и не подтверждает качество модели.

Teams/Zoom/Meet и анализ до завершения записи требуют отдельной интеграции. Для увеличения нагрузки после MVP можно добавить GPU-workers и транзакционную очередь, сохраняя контракт результата и локальное хранение приложения.
