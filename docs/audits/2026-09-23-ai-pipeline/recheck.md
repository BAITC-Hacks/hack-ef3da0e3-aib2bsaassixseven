# Повторный аудит изменённого pipeline

23 сентября 2026. Эта проверка оценивает фактические независимые изменения кода. Она не предполагает, что прежний аудит или план использовались для реализации. Старые отчеты сохраняются как исторические снимки.

## Обновленный вывод

Новая версия заметно лучше обрабатывает известные случаи. Прежние конкретные воспроизведения неправильного года, «не завтра», отмены другого договора, возврата отмененной задачи и переноса имени через отдельную реплику смены темы больше не проваливаются. Поэтому прежний список нельзя целиком предъявлять как актуальные ошибки.

При этом исправления остаются частично привязанными к формулировкам: соседние отрицания даты/отмены и новый способ восстановления адресата дают ошибки. Пайплайн стал сильнее как инструмент подготовки черновика с проверкой секретарем; надежность полностью автоматического назначения поручений пока не доказана.

## Какие изменения обнаружены

По сравнению с первым [снимком](code-fingerprints.json) изменены пять файлов: `__main__.py`, `abstraction.py`, `audio.py`, `compare.py`, `runtime.py`; добавлен `review.py`. ASR adapters, каталог моделей, diarization adapter, models.py, prepare, pyproject.toml и uv.lock первоначально совпали с прежними hashes.

- Исправлен возврат исходной task вместо surviving tasks после salvage; повторно проверяется fallback.
- Добавлены защиты в датах/отменах, обработка смены темы, продолжений, слитных обещаний и принадлежности срока.
- Изменено объединение коротких unlabeled audio gaps между одинаковыми speaker labels.
- Добавлен `--reviewed-corrections`: вставка текста до extraction, привязанная к SHA аудио, с anonymous speaker, копией manifest и его hash.
- Позднее во время аудита добавлены `replacements`: ограниченная интервалом замена текста. Эта реализация и ее tests продолжали изменяться; результат последней проверки указан ниже.
- В provenance добавлен `pipeline_code_sha256`.
- Scorer сравнивает `due_text`, если обе даты null и поле есть в reference.

Это реальные инженерные улучшения. Reviewed insertion следует оценивать как assisted input: она не доказывает, что ASR теперь сам распознает пропущенное имя. `review_note` объясняет происхождение вставки, но не является независимой аудиоразметкой.

## Проверенные версии и тесты

В начале повторной проверки все 12 Python-файлов на Brev совпали с локальными. Агрегатный code hash:

```text

abstraction.py: a54202a504c456492e07a7477b382fb2f157af7c7eb77eae9f83e73c8b82dc03
```

На этой серверной версии шесть ML modules, включая reviewed corrections, дали **103 passed in 1.28s** с `--noconftest -p no:cacheprovider`. Стандартная команда без `--noconftest` проверена заново и по-прежнему падает при загрузке `tests/conftest.py`: `ModuleNotFoundError: No module named 'app'`. ML bundle все еще зависит от web fixtures при обычном запуске tests.

В ходе аудита в другой задаче локально снова изменился `abstraction.py` (mtime 16:50:10 местного времени), в том числе rendering короткого summary. Новый локальный снимок:

```text
d36a308a7a5f429b85123ffdc9c96be38ee071f8d6373980691b25d0b95366c2
abstraction.py: be6177ba3722493a8e25103f32beb12dde474c757f1a828ecc260d9d207dcbea
```

На последней выполненной удаленной сверке Brev оставался на `eeb6…`; не утверждаем, что новый локальный `d36…` уже развернут. [Новые fingerprints](recheck-code-fingerprints.json) фиксируют локальный снимок; [независимая проверка](recheck-verification.md) содержит результаты локальных тестов и повторных probes с границами версий. Основной агент отдельно повторил оставшиеся date/cancel/scorer counterexamples на `d36…`: ошибки сохранились.

**Последняя ограниченная локальная проверка:** во время работы другой задачи сначала наблюдались 104 passed / 2 failed на `d36…` — tests ожидали еще не реализованный `replacements`. Затем реализация появилась, и выполнен один заключительный прогон: **108 collected, 105 passed, 3 failed in 10.86s**, aggregate code hash до/после одинаковый: `60509a297efe0865f148993787bb2b94a9496ea8bc0b251e67d0f61593af305a`. Три падения связаны с полем `utterance_id`, которое новые replacement tests уже передавали, а проверенная schema еще не принимала. При этом сами test files менялись во время исполнения. Это зафиксированная несогласованность незавершенной параллельной работы, а не утверждение о трех дефектах последнего стабильного релиза. Старые два падения не выдаются за текущие; изменения после этого среза не проверялись. Полные fingerprints `d36…` сохранены как предыдущий снимок, не как fingerprint `60509…`.

Первый прогон содержит имя «Тимур Болатович» из correction manifest. Подтверждено наличие traceable вставки, не ее новая независимая человеческая аудиопроверка этим аудитом.

В первом результате ответственные заполнены у всех десяти задач, но это coverage, не доказанные 100% правильных назначений. Во втором теперь присутствует смета, срок поиска поставщика обновлен на «неделя максимум десять дней», справка относится к Жандосу, а недельный срок шаблона не переносится на уведомление. При этом шесть owners остаются null. Большее количество задач и более осторожное воздержание нельзя автоматически оценивать как ухудшение: состав/гранулярность списка изменились.

Все двадцать новых задач требуют review. Встречи остаются недатированными, поэтому nullable calendar deadlines сами по себе не ошибки. Данных для независимой общей accuracy, WER/DER или подтверждения ru/kk/mixed generalization по-прежнему нет.

## Что осталось воспроизводимым

| Проблема | Свежий контрпример / последствие | Оценка |
|---|---|---|
| Отрицание даты | «не 2 октября, а 5 октября» → 2026-10-02, uncertainty=False; «не через три дня, а через пять дней» → +3 дня | P1: прежние примеры исправлены, семейство не закрыто |
| Отрицание отмены | «Не снимаем поручение подготовить договор поставки оборудования» удаляет задачу | P1: явно сохраненное поручение исчезает |
| Семантика scorer | «Утвердить договор» и «Не утверждать договор» с одинаковыми другими полями дают ноль ошибок | P2: выбор модели по такой метрике ненадежен |
| Новая привязка имени | Изолированное имя из reviewed span привязывается к несвязанной задаче через 10 минут, даже при смене темы | P2: `needs_review` есть, но structured owner уже угадан |
| Повторный запуск | Manifest уже в output directory → SameFileError после записи трех результатов | P2: частично обновленный пакет |
| Изменение manifest во время run | В transcript применены прежние bytes, а копируется новый файл; сохраненный hash не совпадает с копией | P2: нарушена воспроизводимость |
| Повтор без corrections | В output остается reviewed_corrections.json от предыдущего запуска | P2: смешанные артефакты |

Лексическое сравнение `due_text` также считает «через две недели» и «через 14 дней» разными сроками. Это частичное улучшение старого scorer, не готовая семантическая оценка.

Точные строки и воспроизведения: [новый code review](recheck-code-findings.md), [независимые результаты](recheck-extra-probe-results.json), [повторная верификация](recheck-verification.md). Counterexamples доказывают возможность ошибки, не ее частоту на реальных совещаниях. Ошибки упаковки воспроизведены настоящим runtime с подменой дорогих audio/model stages; это не утверждение, что свежие серверные пакеты обязательно повреждены.

## Что делать следующим

1. Закрыть оставшиеся отрицания дат/отмен и ограничить direct-address по времени и теме. При неопределенности возвращать unresolved, не первый regex hit.
2. Сохранять неизменные bytes manifest и raw/reviewed transcript до LLM; разделять run directories и завершать пакет атомарно. Сейчас transcript по-прежнему записывается только после extraction.
3. Отделить offline ML tests от web conftest и доработать scorer на согласованных gold links/семантике сроков.
4. Затем измерять raw и assisted режимы отдельно на независимой аудиоразметке. Выбор другой модели пока не является первым необходимым шагом.

Предыдущий план требует сокращения и переупорядочивания: не повторять уже закрытые narrow fixes, не считать code hash полным stage manifest, не принимать reviewed insertion за field evidence/event ledger. [Что именно уже покрыто и что осталось](recheck-plan-impact.md).

Три роли снова отработали цикл: finder исследовал новый flow, researcher пересмотрел следующие шаги, verifier независимо воспроизвел старые и новые cases. Код продукта в рамках повторного аудита не изменялся.
