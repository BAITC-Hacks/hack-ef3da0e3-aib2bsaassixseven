## Вывод

Это работающий исследовательский прототип с хорошей технической основой, но пока недостаточно надежный механизм автоматического назначения поручений. Наиболее существенные подтвержденные дефекты находятся в связывании задач, ответственных, отмен и сроков, а не в размере модели. Оценку точности в процентах сейчас давать нельзя: нет независимо размеченного audio-grounded test set для ru/kk/mixed и диаризации.

Сильные стороны: локальные модели, раздельные стадии и освобождение GPU между ними, временные метки оригинальной записи, строгая схема, ссылки на реплики, закрепленные ревизии моделей и зависимостей, детерминированный Markdown, набор регрессионных тестов. Слабое место: проверка цитаты смешана с эвристическим изменением смысла и состояния поручений; метрики могут принять неверный результат за правильный.

**Рекомендация:** сохранить Community-1 + GigaAM Large CTC + Qwen3.5-9B как baseline, сначала исправить подтвержденные дефекты, построить независимую оценку и только затем выбирать лучшую комбинацию моделей. Подробный [план реализации](../../superpowers/plans/2026-09-23-ai-pipeline-improvements.md).

В двух переданных `provenance.json` есть audio hash и model commit SHA, но нет code/config hash, prompt version, времени стадии, числа retries или peak memory. Поэтому нельзя восстановить производительность этих прогонов или доказать, какой именно вариант кода их создал. Текущий валидатор дает иной результат при replay; версия кода архивного запуска неизвестна. Параллельный новый прогон способен изменить серверные файлы после снимка.

### Конкретные проблемы архивного вывода

1. Во втором совещании справка по встрече с подрядчиками назначена Ерболату Мухтаровичу. Реплика u26 (93.080–98.412 s) склеивает поручение по предыдущей теме, короткое «сделаю» и обращение к следующему докладчику. Имя в том же ASR turn не доказывает владельца задачи. Markdown относит справку к Жандосу; поздний transcript recap u47 это поддерживает.
2. Там же срок поиска поставщика остается «за две недели», хотя u46 содержит «неделя максимум десять дней». Это изменение срока не отражено в ZIP.
3. Срок «не больше недели» из u49 про новый шаблон договора перенесен также на уведомление и правила выставления счетов. Это утечка срока между соседними задачами.
4. Поручение подготовить смету отброшено: warnings указывают на цитату, разбитую между u36 и u37 («за неделю дам смету подоп» / «группам»). Отсутствующий кандидат нельзя вернуть простым повторным запуском валидатора.
5. В первом совещании несколько ответов в диалоге об инциденте имеют label председателя; это повод размечать speaker boundaries и короткие реплики. Число участников Markdown нельзя автоматически считать эталонным числом различимых голосов записи.

**Существенная поправка:** replay архивного JSON через текущий `validate_evidence` уже меняет срок поиска поставщика, очищает лишние сроки, восстанавливает некоторые имена и меняет владельца справки на Жандоса. Это подтверждено двумя агентами без загрузки моделей. Поэтому пункты 1–3 нельзя объявлять доказанными текущими end-to-end регрессиями. Их исправление в новом полном прогоне пока не измерено; рядом найдены новые ошибки эвристик.

### Почему Markdown пока не gold

Протоколы полезны для выявления бизнес-сценариев и ожидаемой структуры. Они не имеют временной разметки и могут расходиться с записью. Например, во втором протоколе нет срока на шаблон, но ASR transcript его содержит; итоговый срок поиска поставщика также отличается. Сохраненный на Brev `audit_asr.json` содержит альтернативные Whisper-гипотезы, поддерживающие эти расхождения. Согласие двух ASR — повод проверить аудио, а не человеческий ground truth.

Поэтому нельзя честно посчитать WER, DER, task recall или качество казахского на этих Markdown как на готовом эталоне. Требуется разметка непосредственно по MP3. Наличие казахских имен не является тестом понимания казахской или смешанной речи.

## Подтвержденные ошибки текущего кода

| ID | Severity | Что воспроизведено | Последствие |
|---|---|---|---|
| E1 | P1 | `до 2 октября 2027 года` → 2026-10-02; `не завтра, а через три дня` → завтра; uncertainty=False | Ошибочный точный срок после корректного ASR |
| E2 | P1 | Отмена аренды офиса удаляет задачу договора поставки оборудования по общему stem `дого` | Тихая потеря действующего поручения |
| E3 | P1 | При salvage после некорректного факта добавляется исходная task, уже удаленная validation | Отмененная задача возвращается в итог |
| E4 | P2 | Имя прежнего адресата переносится через явную смену темы | Неподтвержденный ответственный в структурированном поле |
| E5 | P2 | Разные `due_text` не считаются ошибкой, когда обе даты null | Завышенная оценка качества сроков |
| V1 | P2 | `Утвердить договор` и `Не утверждать договор` могут считаться правильным action match | Неверная семантика получает идеальный score |

Репродукции и точные строки находятся в [findings](error-findings.md) и [probes](verifier_probes.py). P0 severity не установлен. «Первый этап» плана означает порядок работ, а не аварийную критичность.

## Готовность к исходному кейсу

| Область | Оценка по имеющимся доказательствам |
|---|---|
| Локальный batch inference | Есть, работает на предоставленном NVIDIA сервере; изоляция от сети не проверена сетевым трассированием |
| Русский ASR | Реальные результаты есть, количественной независимой оценки нет |
| Казахский / смешанная речь | Кандидаты есть; качество на целевых встречах не доказано |
| Диаризация | Есть anonymous labels; надежное speaker-to-person mapping отсутствует |
| Ответственный / срок / отмена | Есть extraction и проверка цитат, но подтверждены semantic bugs |
| Итоговый протокол | JSON и Markdown есть; pipeline не создает PDF/DOCX |
| Пользовательский сценарий | Offline CLI отделен от FastAPI; API содержит профиль/health, dashboard остается starter, нет upload → review → export |

Для демонстрации наиболее полезен секретарский review со ссылкой на аудиофрагмент и ясными причинами неопределенности. Автоматические рассылки/напоминания следует подключать к подтвержденным поручениям после исправления логики. Не следует расширять scope до live meeting bots, fine-tuning или смены serving engine до измерений.
